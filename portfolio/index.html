Game Overview

10..9..8.. is a 2D top-down dungeon exploration game built around a simple constraint: the player has only 10 steps. Inspired by chess and roguelike games, the player explores a dungeon while deciding how to spend a limited step resource on movement, combat, and progression.

Steps function as more than movement points. Moving consumes them, enemy attacks reduce them, and purchasing items can also cost steps. Healing items restore steps, making the same resource function as movement capacity, survivability, and currency. If the player's remaining steps reach zero, the run ends.

Players progress through semi-randomly selected dungeon layouts, fight or avoid enemies with different movement patterns, reach stairs to advance between floors, visit store floors to purchase equipment, and ultimately confront the Chess King.

Game Features

The game contains three themed stages — Chessboard, Forest, and Castle — with multiple dungeon floors and store areas between stages. Maps are assembled from separate text-based data for tile layouts, enemies, and traps, allowing stage layouts to be selected semi-randomly at runtime.

Enemies are inspired by chess pieces but have distinct movement and attack behaviors. Players must manage their limited steps while responding to melee enemies, long-range attacks, traps, and the final Chess King encounter. Consumable items restore steps, while equipment such as axes, spears, shields, and boots introduces additional choices through rarity, durability, cost, and specialized effects.

My Role

I served as the Technical Lead for the project, taking responsibility for major technical decisions, engine architecture, and integration across the game.

The project was built on a custom C++ engine developed through DigiPen's Game Implementation Techniques coursework. I worked on organizing reusable engine functionality separately from game-specific gameplay logic and helped coordinate integration between the different systems used by the team.

Technical Architecture

The engine organizes runtime objects through a GameObjectManager and component-oriented architecture. Game objects can be updated and drawn collectively, while draw priorities are used to determine rendering order.

Game-level functionality is divided among systems including a TurnManager, EnemyManager, ItemManager, UI system, and audio wrapper. Reusable components such as Timer, Sprite, and Texture provide common functionality for gameplay objects and rendering.

Game Overview

Dragonic Tactics is a 2D turn-based tactical RPG that reverses the traditional fantasy RPG premise: instead of controlling a party of heroes, the player becomes a dragon defending its territory against a group of adventurers.

Combat takes place on a grid and emphasizes positioning, resource management, ability usage, and interaction with independently controlled adventurers.

Game Features

The game's core design focuses on strategic positioning, limited-resource management, and asymmetric combat. The dragon is significantly more powerful than an individual adventurer, but must manage action points, spell slots, movement, and positioning while fighting an opposing party with complementary roles.

Adventurers are divided into distinct archetypes such as Fighter, Wizard, Cleric, and Rogue, each emphasizing different behaviors including frontline pressure, ranged damage, healing and support, or mobility and flanking. The dragon uses a varied set of abilities that can deal damage, apply status effects, manipulate enemy positions, and alter the battlefield by creating obstacles or hazardous terrain.

Facing direction, attack ranges, area-based targeting, and status effects further make spatial relationships important throughout combat.

Rendering System

I implemented three rendering approaches to explore different trade-offs between simplicity, CPU workload, GPU workload, memory transfer, and draw-call reduction.

Immediate Renderer

The immediate renderer keeps a single unit quad on the GPU and reuses it for every sprite. Each request uploads transform, texture-region, depth, and tint information through uniforms before issuing an individual draw call.

The architecture is straightforward and requires no batching or flushing, making it appropriate for the scale of the final game. For that reason, the immediate renderer remained the default renderer used by Dragonic Tactics.

Batch Renderer

The batch renderer accumulates multiple sprites into a larger CPU-side vertex buffer before submitting them together.

Instead of uploading a model transform for each sprite, the CPU calculates transformed vertex positions in advance and stores position, texture coordinates, tint, texture slot, and depth directly in the vertex data.

A texture-slot system allows multiple textures to participate in the same batch, reducing the number of draw calls required to render larger groups of sprites.

Instanced Renderer

The instanced renderer keeps a single unit quad on the GPU and stores only per-sprite rendering information in an instance buffer.

Unlike the batch renderer, the CPU does not generate transformed vertices for every sprite. Transformation is performed by the GPU using per-instance data.

This reduces per-sprite transfer from approximately 112 bytes in the batch representation to 52 bytes in the instanced representation, while retaining the ability to draw many sprites together.

Batch rendering and instancing were implemented proactively because the engine was expected to handle more sprites as development progressed. Rather than waiting for rendering scalability to become a problem, I implemented alternative rendering architectures early and compared their trade-offs while preserving the simpler immediate renderer when it was sufficient for the actual game.

Additional Engine Work

EventBus

I designed an EventBus-based communication system to decouple engine and gameplay systems where direct dependencies were unnecessary.

The architecture still allowed direct references where subsystems required tighter integration, rather than forcing every interaction through the event system.

Virtual Resolution

The rendering pipeline includes a virtual-resolution system that allows game content to be authored against a consistent logical resolution while being presented correctly across different display sizes.
